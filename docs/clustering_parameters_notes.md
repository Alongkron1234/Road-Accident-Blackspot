# `int_accident_clusters` — เหตุผลการเลือก parameter (Issue 08 step 6-7)

## SRID ที่ใช้: 32647 (UTM Zone 47N)

เช็คจากข้อมูลจริงใน `stg_accidents` พบว่า ~85% ของข้อมูลอยู่ในโซน 47N (longitude < 102°):

| source | zone_47n | zone_48n |
|---|---|---|
| arms_csv | 9,872 | 1,584 (13.8%) |
| exat | 39,422 | 0 |
| arms_json | 700 | 136 (16.3%) |

เลือกใช้ SRID เดียว (47N) กับข้อมูลทั้งหมดเพื่อความง่าย ยอมรับว่าข้อมูลฝั่งตะวันออก (~14-16% ของ
ARMS) จะมีระยะทางคลาดเคลื่อนเล็กน้อยเพราะอยู่นอกโซนหลัก — ไม่แยก query 2 โซนเพราะ clustering นี้
เป็นการหา "จุดเสี่ยง" ระดับภาพรวม ไม่ใช่งานที่ต้องการความแม่นยำระดับเซนติเมตร

## eps: ทดลองปรับ 300 → 150 → 50 (สุดท้ายใช้ 50 เมตร)

`PLAN.md` แนะนำช่วง 200-500 เมตร แต่ทดสอบจริงแล้วพบปัญหา **chaining effect** ของ DBSCAN:
DBSCAN จับกลุ่มแบบ "ต่อลูกโซ่" ถ้าถนนเส้นไหนมีอุบัติเหตุเกิดถี่ต่อเนื่องกันตลอดสาย (จุดห่างกัน
ไม่เกิน eps ทีละคู่) ทั้งเส้นจะรวมเป็น cluster เดียวได้แม้ปลายสองข้างจะห่างกันหลายกิโลเมตร

| eps | max cluster size | ขนาดจริงบนแผนที่ |
|---|---|---|
| 300 (ตาม PLAN.md) | 1,748 | ~4.5 กม. เหนือ-ใต้ ❌ ใหญ่เกินจะเรียกว่า "จุดเสี่ยง" |
| 150 | 1,724 | แทบไม่ต่างจากเดิม |
| **50** | **45** (หลัง fix dedup) | **~560 เมตร** ✅ สมเหตุสมผล |

**สรุป: เบี่ยงจากช่วงที่ PLAN.md แนะนำ (200-500m) มาใช้ 50 เมตรแทน** เพราะข้อมูลจริงมีความหนาแน่น
สูงกว่าที่คาดไว้ (อุบัติเหตุเกิดถี่ตามถนนสายหลัก) — eps ในช่วงที่แนะนำทำให้เกิด chaining effect
รุนแรงจนไม่มีความหมายเป็น "จุดเสี่ยง" อีกต่อไป

## minpoints: 3

ต้องมีอุบัติเหตุเกิดซ้ำอย่างน้อย 3 ครั้ง ถึงนับเป็น cluster จริง (ค่าเริ่มต้นมาตรฐานที่ใช้กันทั่วไป
สำหรับ DBSCAN ไม่ได้ทดลองปรับค่าอื่นเพิ่มเติมในรอบนี้)

## ทำไมไม่แยก parameter ตาม `source` (ARMS vs EXAT)

พิจารณาแล้วว่า**ไม่จำเป็น** เพราะผลลัพธ์ที่ได้จากพารามิเตอร์เดียวกันสมเหตุสมผลอยู่แล้วทั้งสองฝั่ง:
- **EXAT** ได้พอดี 9 cluster เท่ากับจำนวนทางด่วนใน seed `expw_step_coordinates` — เพราะพิกัด EXAT
  ซ้ำกันเป๊ะทั้งสาย (เป็นพิกัดตัวแทน ไม่ใช่จุดเกิดเหตุจริง ตามที่บันทึกไว้ตั้งแต่ Issue 07) ทำให้
  ระยะห่างระหว่างจุดในสายเดียวกัน = 0 เสมอ จับกลุ่มเป็นก้อนเดียวโดยธรรมชาติไม่ว่า eps จะเป็นเท่าไหร่
- **ARMS** ได้ cluster ขนาดกระจายตัวหลักร้อยเมตร สมเหตุสมผลกับ eps=50

**ข้อจำกัดที่ต้องรู้ไว้ (สืบทอดจาก Issue 07):** cluster ฝั่ง EXAT สื่อความหมายระดับ
**"เกิดบนทางด่วนสายไหน"** ไม่ใช่ **"เกิดจุดไหนบนทางด่วน"** เพราะพิกัดต้นทางหยาบกว่า ARMS มาก
ไม่ใช่ข้อจำกัดของ clustering algorithm แต่เป็นข้อจำกัดของคุณภาพพิกัดต้นทาง

## ปัญหาที่เจอระหว่างทางและแก้ไปแล้ว: ข้อมูลสะสมซ้ำข้ามวัน

ก่อนปรับ eps พบว่า `stg_accidents` มี `accident_id` ซ้ำกันเยอะมาก (12,931 กลุ่ม) เพราะ
`raw_arms`/`raw_exat` สะสมข้อมูลจากการรัน DAG หลายวัน (idempotency ที่ทำไว้ใน Issue 05 กันซ้ำแค่
ระดับ "ชื่อไฟล์" ไม่ใช่ระดับ "เนื้อหาอุบัติเหตุ" เพราะชื่อไฟล์มี timestamp วันที่ติดอยู่)

**แก้โดยเพิ่ม dedup ใน `stg_accidents.sql`** — ใช้ `ROW_NUMBER() OVER (PARTITION BY accident_id,
source ORDER BY loaded_at DESC)` เก็บแค่แถวล่าสุดต่ออุบัติเหตุ ตัดของเก่าทิ้ง ยืนยันผลแล้วว่า
`arms_json` ได้ 209 แถวตรงกับ Issue 04 เป๊ะ, duplicate group = 0
